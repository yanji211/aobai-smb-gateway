# 07 · 快同步协议（fsgw-sync）

> 一句话：**用一条自己的 HTTP 协议把目录推到共享根里，分块并行、小文件打包、断了能续。**
> 不替代 SMB，也不打算替代——它只补 SMB 在"大批量搬运"上补不上的三件事。

## 1. 为什么不用 SMB 复制

| 现象 | SMB 的机制 | 快同步的做法 |
| --- | --- | --- |
| 大文件传到一半断了，重来 | 一条会话里的写是顺序的，没有"已传偏移"的概念；客户端重连只能从头写 | 块级位图：每块落盘即记一位，重跑只补缺的块 |
| 多线程没提速 | 一条 SMB 会话内请求串行；开多线程只是把请求排队，还在一个核上 | 每个块是独立的 HTTP 请求，天然可以 N 条连接并行写同一文件的不同偏移 |
| 几千个小文件磨死人 | 每个文件至少一次 create + write + close 往返 | 小文件打包成一次请求（一帧一个文件），500 个文件 = 1 次往返 |
| 复制完不知道对不对 | 只有 NTSTATUS，没有内容校验 | 每块带 sha256，服务端逐块验；收尾再对已落盘文件做存在性/大小复核 |

## 2. 数据流

```
fsgw-sync (客户端)                     fsgw (服务端，默认 :8445)
  扫描本地目录                                │
  ├─ POST /v1/session        （NDJSON 清单）──► 建会话，落 SQLite
  ├─ GET  /v1/session/{id}/plan （NDJSON）──► 每文件决策 skip/put
  │                                            │
  ├─ 小文件：POST /v1/session/{id}/bundle ────► 解析帧 → 临时文件 → 改名
  │                                            │
  ├─ 大文件：GET  .../file/{fid}/state ──────► 已收到哪些块（断点续传）
  │          PUT  .../file/{fid}/chunk/{i} ──► pwrite 到 .part + 置位
  │          POST .../file/{fid}/commit ─────► fsync → rename 到最终路径
  │                                            │
  └─ POST /v1/session/{id}/finish ───────────► 逐文件复核存在性与大小，出汇总
```

关键设计：**落盘先写暂存，最后一步才改名。**
暂存放在共享根内部的 `.fsgw-sync/<sid>/`（必须同一文件系统，rename 才是原子的）。
所以目标文件在任何时刻只可能是"旧的完整版本"或"新的完整版本"，不会出现半个文件——
这正是 SMB 复制大文件失败时最要命的地方。

## 3. 端点

所有 `/v1/*` 需要 `Authorization: Bearer <sync token>`（也接受 `X-FSGW-Sync-Token`）。
token 在 `<data_dir>/sync.token`，与控制台 token 分离：它只能写文件，不能停服务、改配置。

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/v1/info` | 协议版本、块大小、上限、是否支持 bundle/resume |
| POST | `/v1/session` | 提交清单（NDJSON），返回 `session_id`；带 `session` 字段则续传 |
| GET | `/v1/session/{sid}` | 会话汇总（状态、各动作计数） |
| GET | `/v1/session/{sid}/plan` | 逐文件决策，NDJSON 流式返回 |
| GET | `/v1/session/{sid}/file/{fid}/state` | 该文件已收到的块下标 |
| PUT | `/v1/session/{sid}/file/{fid}/chunk/{i}` | 上传第 i 块，body 为原始字节 |
| POST | `/v1/session/{sid}/file/{fid}/commit` | 校验完整并改名落盘 |
| POST | `/v1/session/{sid}/bundle` | 小文件打包（帧格式见第 5 节） |
| POST | `/v1/session/{sid}/finish` | 收尾：复核 + 汇总 + 清理暂存 |
| DELETE | `/v1/session/{sid}` | 放弃会话并清理暂存 |

### 3.1 清单（NDJSON）

第一行是表头，之后一行一个文件。用 NDJSON 而不是一个大 JSON 数组，是因为
几十万文件的清单一次性反序列化会把内存顶到几百 MB；流式读一行处理一行，内存是常数级。

```json
{"root":"main","dest":"相册/2026","client":"fsgw-sync/0.1","checksum":false}
{"p":"视频/长江夜景.mp4","s":167772160,"t":1762345678,"m":420}
{"p":"文档/说明.txt","s":37,"t":1762345600,"m":420}
```

### 3.2 决策规则（plan）

| 条件 | 动作 | 原因 |
| --- | --- | --- |
| 目标不存在 / 不是普通文件 | `put` | missing |
| 大小不同 | `put` | size |
| `checksum:true` 且内容 sha 不同 | `put` | content |
| `checksum:false` 且 mtime 差 > 2s | `put` | mtime |
| 其余 | `skip` | same / checksum |

默认走 mtime（rsync 的老办法）：快，但对方时间戳被改过会误判成"没变"。
真要正确性就用 `-checksum`，代价是两边都要读一遍内容。

## 4. 分块与断点续传

```
块大小            chunk_mb（默认 4 MiB）
块数 n            ceil(size / chunk)
第 i 块偏移       i * chunk
暂存文件          <root>/.fsgw-sync/<sid>/<fid>.part
位图              <root>/.fsgw-sync/<sid>/<fid>.map   （每块 1 bit）
fid               sha1(路径小写)[:8]，与路径一一对应
```

- 收到块 → `pwrite(offset)` 到 `.part` → 置位 `.map`。**重复上传同一块是幂等的**。
- 位图在盘上而不是内存里，所以进程被杀、机器重启后仍然知道"哪几块已经在了"。
- 会话 TTL（默认 72h）到期，服务端连 `.part` 一起清理；共享根里没有对应会话的
  孤儿暂存目录也会在启动时被扫掉。

实测：预置 3 块（第 0/10/20 块）后让客户端接管，客户端打印
`续传 大文件.bin：已有 3/40 块`，只补 37 块，最终 sha256 与源文件一致。

## 5. 小文件打包（bundle）

```
"FGB1"
[u32 hdrLen][hdr JSON][data ...]   × N
```

`hdr` 与清单条目同构（`p/s/t/m/h`）。选这个格式而不是 multipart：multipart 要扫全流
找边界、还得把整段读进内存；这里长度就在头部，读完头按长度拷贝，零解析开销。

服务端对每个文件：建目录 → 写临时文件（随机名）→ 校验 sha → 改名 → 设时间/权限。
**返回 `written`/`frames`/`failed` 三个数**，客户端必须核对 `written == 本地发出数`。
这一条不是洁癖：第一版只看 HTTP 200，结果 39 个文件"报告成功、磁盘上却没有"。

## 6. 一致性保证

| 层级 | 手段 |
| --- | --- |
| 单块 | `X-Chunk-SHA256`，服务端逐块校验，错就 400，客户端重传 |
| 单文件 | commit 前校验暂存大小 == 声明大小；`fsync` 后 `rename` |
| 单文件（可选） | `verify: full` 时再整文件算 sha256，与清单比对 |
| 整次同步 | finish 时对每个 `done` 文件 stat 一遍，缺失或大小不符降级为 `fail` |
| 传输中断 | 位图保留，重跑只补缺块；会话可跨进程/跨重启续传 |

## 7. 安全

| 边界 | 规则 |
| --- | --- |
| 鉴权 | 每个请求都验 token（常量时间比较）；无匿名通道 |
| 路径 | 拒绝绝对路径、盘符、`..`、控制字符；`dest` 与文件名都规范化；最后用 `filepath.Rel` 回算确认没有逃出根 |
| 保留目录 | 任何一段是 `.fsgw-sync` 直接拒绝，防止把暂存区当普通目录写 |
| 根白名单 | 只允许 `shares[].writable: true` 的根；`sync.roots` 可再收窄 |
| 暴露面 | 同步服务属于**局域网面**：总开关 OFF / 仅外部时不监听 |
| 权限 | token 文件 0600；进度日志只记路径不记内容 |

## 8. 性能（本机回环，Windows，D 盘）

数据集：803 个文件 / 223.5 MiB（160 MiB + 50 MiB 两个大文件，其余为 0–64 KiB 小文件）

| 场景 | 结果 |
| --- | --- |
| 首次全量 | 8.4 s，26.5 MiB/s |
| 增量（无变化） | 0 个文件，扫描即结束 |
| 改动 5 个（含 50 MiB 大文件） | 1.6 s，30.8 MiB/s |
| 单文件 160 MiB（4 MiB 块，8 并发） | 2.5 s，64 MiB/s |

同一台机器、同一块盘，之前 SMB 复制的实测是 **2.5–5 MiB/s**，且大文件常在中途断。
差距不在"协议更先进"，在于：SMB 一条会话内串行，而这里同一文件能有 8 条连接同时写不同偏移。

调参建议：

- 千兆有线：`-workers 8`、`-chunk-mb 4`
- 2.5G/10G：`-workers 16`、`-chunk-mb 8`
- 小文件特别多（>5 万）：把 `-bundle-kb` 提到 512，减少包数

### 8.1 实网（Win11 无线 192.0.2.10 → 服务器 192.0.2.11）

数据集：603 个文件 / 120.6 MiB（120 MiB 单个大文件 + 600 个 0–2 KiB 小文件 + 中文名/带空格文件名）

| 场景 | 结果 |
| --- | --- |
| 首次全量（`-workers 8 -file-workers 4`） | 20.4 s，5.9 MiB/s |
| 增量（无变化） | 0.32 s，603 个全部跳过 |
| 常驻 `-watch 5s`：新增 1 个 + 改 1 个 | 下一轮 240 ms 内补齐 |
| 落盘校验 | 604 个文件、总字节数完全一致；120 MiB 文件 sha256 一致；没有残留 `.part`/`.map`/`.fsgw-sync` |

本机无线协商速率 120 Mbps（≈15 MB/s 理论上限），实测 5.9 MiB/s ≈ 6.2 MB/s ≈ 50 Mbps，
约合协商速率的四成——这是 802.11n 单流的常见有效吞吐，**瓶颈在空口，不在协议**：
同一台机器、同一张网卡上 SMB 复制只有 2.5–5 MiB/s，且大文件会半途断掉。
换千兆有线再测才有意义，届时按上面的调参建议把 `-workers` 提到 8–16。

一次真实的大目录搬运（`Desktop\desk88` → `/srv/share/desk88`）：

| 项 | 值 |
| --- | --- |
| 规模 | 471,609 个文件 / 49.88 GiB（含 5 GB gguf 模型、4.3 GB ISO、1.8 GB MTS） |
| 清单 + 计划阶段 | 21:30:35 → 21:36:30（约 6 分钟，纯 CPU/写库，没有字节在传） |
| 小文件阶段 | 47 万个落盘约 18 分钟（360–520 文件/秒，受目标盘建文件速度限制） |
| 大文件阶段 | 稳定 6–7.7 MiB/s，空口（120 Mbps 无线）是瓶颈 |
| 整体 | **2 小时 29 分 43 秒，均速 5.7 MiB/s**，0 失败 |
| 校验 | 两侧文件数与总字节完全一致（471,609 / 53,559,581,649，差值 0）；抽查 1.2 GB 文件 sha256 相同；暂存目录已自动清空 |

同一批数据用 SMB 复制，历史实测是 2.5–5 MiB/s 且大文件会断——`fsgw-sync` 的价值主要在
"不停中途、可续传、数量可控"，而不是单纯追峰值。

期间服务端出现过 `监听缓冲溢出，执行子树重建` 连刷 800+ 条（47 万文件涌入把 inotify 队列打爆，
每条都整树重扫）。已改为**去抖 + 单飞**：只允许一个重建在跑，期间的溢出只置脏标记，跑完补一轮。

## 9. 已知限制

1. **只做单向 push，不删除目标多余文件。** 删除是不可逆操作，第一版不给。
2. **不做双向比较**（没有 pull，也没有冲突合并）。需要取回请用 SMB / WebDAV。
3. **单次清单上限默认 100 万文件**（`sync.max_files`，可调 1000–500 万）。客户端扫描后会先比对服务端
   的 `max_files`，超了直接报错并提示用 `-exclude` 或分目录，不会传到一半才失败。
   清单越大，建会话 + 出计划这一段越慢（纯 CPU 与 SQLite 写入）：实测 47 万文件约 5 分钟，
   这段时间没有字节在传，属正常；传输阶段才开始走动。
4. **mtime 判断有 2 秒容差**；跨文件系统（FAT）时时间精度差异不会反复触发重传。
5. **同名文件覆盖时先删后改名**，这一瞬间目标文件不存在；被占用的文件会明确报错，
   不会静默失败。
6. **不保留符号链接/ACL/扩展属性**，只保留内容、mtime、权限位。

## 10. 排错

| 症状 | 查什么 |
| --- | --- |
| `401 token 无效` | `sudo cat <data_dir>/sync.token`；控制台「快同步」卡片上的命令可直接复制 |
| `共享根 "x" 不存在或不可写` | `shares[].writable` 是否为 true；`sync.roots` 是否把它排除了 |
| `连接被拒绝` | 总开关是否在「局域网/全部」；`ss -ltn | grep 8445`；防火墙 |
| 卡在某个块 | 客户端会自动重试 4 次；服务端日志里看 `写块失败` |
| `打包只写入 N/M 个` | 看响应里的 `errors`，通常是目标文件被占用或路径非法 |
| 明明传完却报 fail | finish 的落盘复核发现了缺失/大小不符——这是兜底在起作用，重跑即可补齐 |
