01 技术设计说明

1. 文档定位

本文把策略讨论稿翻译成可编码的工程设计。策略层的共识（局域网直读直写、外部只读、SQLite 唯一真相源、移动零版本、开关即安全）全部继承，不再重复论证；本文只回答"具体怎么实现"以及"哪些地方做不到"。

三处工程调整及其理由收敛在 04-决策点与风险登记.md，本文在涉及处标注决策编号，例如 [D-02]。

2. 目标与非目标

2.1 第一版目标

  • 局域网内电视、手机、PC 免装 App 访问 D:\share，可读可写
  • 外部（公网或隧道）只读浏览与下载，含历史版本
  • 文件整理（移动、重命名、建目录）不产生版本链增长
  • 网关关闭后本机不残留任何监听端口与防火墙放行规则
  • 索引与磁盘不一致时可自愈，且自愈过程不扫全盘
  • 提供本机网页控制台（HTML 前端 + Go 后端）：开关、共享目录、索引统计、诊断与审计在一个页面上闭环

2.2 非目标

  • 不做多用户、角色、ACL 体系。外部面一个共享口令，局域网面匿名或单账户
  • 不做块级快照、不做全量备份、不做 Git 式分支
  • 不做跨平台一致的 SMB 协议栈自研（见 D-01）
  • 不做云端同步、不做去重存储引擎
  • 不做远程管理界面。控制台只绑回环，不提供"从手机管理网关"的能力
  • 不做移动端 App、不做托盘常驻 UI（控制台就是唯一图形界面，浏览器即宿主）
  • 不接管系统盘与用户主目录，共享根只能是显式配置的目录白名单

关键不变量：

  1. 数据库是唯一真相源。目录列举、Stat、路径解析一律查库，不 os.Stat。
  2. 磁盘只提供字节。读取失败如实报错，不反向修正数据库。
  3. 写路径要么入库要么不可见。结构性变更走事务，提交后才对外生效。
  4. SMB 来源与网关来源互斥。网关自己经手的写操作同步更新库，并抑制对应 fsnotify 事件，避免重复记账。

4. 进程与生命周期

单进程，无外部依赖（SQLite 嵌入、纯 Go 驱动、CGO 关闭）。

运行形态：

形态用途权限
fsgw run前台 console，开发调试与验收用需管理员（绑定 445、增删防火墙规则）
fsgw service install/start/stop注册为 Windows 服务（x/sys/windows/svc），开机自启LocalSystem
fsgw on / off / status控制面客户端，向运行中的进程投递指令普通用户（走回环 HTTP API + token，见第 11 节）
fsgw ui生成带 token 的地址并打开默认浏览器普通用户

启动序列：

读配置 → 校验（路径存在、可写、非系统目录）→ 打开 SQLite → 迁移
  → 加载共享白名单 → 加载 desired_state（默认 OFF）
  → 若 desired_state != OFF：按状态机执行开启（失败则回落到 OFF 并告警）
  → 启动 watcher（ON/OFF 都跑，索引需要持续维护）
  → 启动 ctlapi（127.0.0.1:8444，内嵌 webui 静态资源）

注意：索引维护与开关解耦。开关只影响"对外暴露的协议面"，索引始终运行；否则每次开启都要重扫。

5.2 转换顺序（不可调换）

开启方向，从外到内以避免"端口开了但服务没起"的窗口：

  1. 校验目标状态的前置条件（共享根可读、端口未被占用、证书存在）
  2. 创建防火墙规则（幂等：先删同名再建）
  3. 启动对应 listener，等待就绪探针
  4. 自检：本机连一次自己的端口，失败则回滚
  5. 持久化 desired_state，写审计

关闭方向，从内到外：

  1. 停止 listener（等待在途连接最多 5s，超时强制）
  2. 移除防火墙规则
  3. 持久化 desired_state=OFF，写审计

任一步失败：执行反向清理，最终状态回落到 OFF，并把失败阶段写进 state.json.last_error，控制面 status 直接展示。不允许停在中间态。

5.3 崩溃恢复

state.json 记录 desired_state 与实际 applied_state。进程启动时若二者不一致，一律按 OFF 启动并告警，不猜测用户意图。这样即使上次是异常退出，也不会有端口残留。

6. 平台抽象层

四个接口，Windows 实现优先落地，Linux 只留空实现（编译可通过、运行返回 ErrNotImplemented）。

6.1 fileid

type FileID struct {
    VolumeSerial uint32
    ID           [16]byte // FILE_ID_INFO 的 128 位；退化路径时高 8 字节为 0
}

type Provider interface {
    Of(path string) (FileID, error)
}

Windows 实现要点：

  • CreateFileW 打开句柄，目录必须带 FILE_FLAG_BACKUP_SEMANTICS，文件带 FILE_FLAG_OPEN_REPARSE_POINT 防止跟随符号链接与目录联接
  • 优先 GetFileInformationByHandleEx(FileIdInfo) 取 128 位 ID 与卷序列号
  • 不支持时退化为 GetFileInformationByHandle 的 nFileIndexHigh/Low（64 位），此时高 8 字节补零，并在 objects.native_file_id 里用 v1: 前缀区分，避免与 128 位 ID 冲突
  • 句柄必须在取完 ID 后立即 CloseHandle，监听热路径上这是主要开销，量级约数十微秒，可接受

6.2 watcher

type Op int // Create | Write | Rename | Remove

type Event struct {
    Op      Op
    Path    string // 绝对 Windows 路径（长路径已加 \\?\ 前缀）
    OldPath string // 仅 Rename 有效
    IsDir   bool
}

type Watcher interface {
    Add(root string) error
    Events() <-chan Event
    Overflow() <-chan string // 缓冲溢出，携带需要范围重建的子树根
    Close() error
}

Windows 实现要点（不依赖第三方递归封装，直接调 ReadDirectoryChangesW）：

  • bWatchSubtree=TRUE，FILE_NOTIFY_CHANGE_FILE_NAME | DIR_NAME | SIZE | LAST_WRITE | CREATION
  • 缓冲区 64 KiB，单缓冲轮转；溢出返回 ERROR_NOTIFY_ENUM_DIR 时向 Overflow() 投递该子树根
  • 重命名天然成对：FILE_ACTION_RENAMED_OLD_NAME 紧跟 FILE_ACTION_RENAMED_NEW_NAME，无需像 inotify 那样靠 cookie 配对，但仍要处理"只收到一半"的情况（见 02 的 pending_moves）
  • 事件只给路径不给 ID，因此每个事件都要开一次句柄取 FileID。删除事件无法取 ID，只能用路径匹配库中记录

6.3 firewall

type Rule struct {
    Name    string // 统一前缀 FSGW-
    Dir     string // in
    Action  string // allow
    Proto   string // tcp | udp
    LocalPort  int
    RemoteIP   string // localsubnet | any
    Profile    string // private | domain,private

type Firewall interface {

实现走 netsh advfirewall firewall，理由：命令可审计、可回滚、失败信息明确，比 COM 的 INetFwPolicy2 更容易定位问题。每条规则的创建形式为 delete rule name=X 后 add rule，保证幂等。

7. 索引与监听

7.1 事件分类

事件进入后先做归属判断，再分流。这一步决定了后面所有语义是否正确。

事件来源判定方式处理
网关自身（WebDAV 写、快照、清理）写入前在 suppress 表登记 (路径, 期望 mtime/size)直接丢弃，不做任何记账
SMB 客户端写入路径在 SMB 共享白名单内且未登记 suppress归为 source=smb，走 best-effort 快照
本机应用直接修改其余归为 source=local，只保证索引版本链

suppress 表的键包含期望的 mtime 与 size：只有实际事件与预期一致才丢弃，避免把"网关写完但用户同时也在改"的情况误吞。

7.2 防抖与合并

  • 结构性变更（Create / Rename / Remove）：100–200ms 窗口，保证移动配对完整
  • 内容变更（Write）：300–500ms 窗口，同一文件窗口内多个 Write 合并为一次版本追加
  • 大文件写入会产生持续 Write 事件流。策略：当同一 FileID 的 Write 事件间隔小于 500ms 时持续续期，直到静默满窗口才落一次版本；期间状态为 writing，ReadDir 可见但标记为"写入中"

7.3 溢出与漏事件

溢出不等于需要全盘扫描。处理方式：

  1. 从 Overflow() 拿到子树根
  2. 对该子树做一次范围重建：ReadDir 递归遍历（限制最大深度与节点数，超限则跳过并告警）
  3. 与库中该子树的记录做差集，补插、改删，全部在一个事务内完成
  4. 记录 reconcile 审计事件，含耗时与节点数

另外提供低频校验任务（默认每 6 小时，仅对最近 24 小时内变更过的 object 抽查存在性），兜住监听启动前与半途漏掉的事件。

7.4 写入顺序

见 02-数据模型与事务.md 第 4 节。这里只强调一条：先库后可见。结构性变更事务提交前，新路径不出现在任何 ReadDir 结果里。

8. VFS 与路径

VFS 是三个协议面的公共下层，负责三件事：路径规范化、白名单校验、穿越防护。

规范化规则：

  • 输入一律转绝对路径，扩展为 \\?\ 长路径形式（超过 240 字符必须）
  • 统一分隔符为 \ 落盘、/ 入库存 path_key
  • Windows 大小写不敏感：path_key = lower(path)；显示名保留原始大小写。配置项 case_sensitive 默认为 false
  • 拒绝并记录以下输入：含 .. 段、含 ADS 冒号（file.txt:stream）、含设备名（CON、NUL、COM1 等）、末尾带空格或点、路径长度超限
  • 解析软链接与目录联接：解析后的真实路径必须仍在共享根内，否则拒绝

白名单校验走 share_dirs 表：一次查库判定 (share_id, rel_path) 的最长前缀，命中才放行。可写性继承：子目录默认继承父级，允许显式覆盖为只读。

9. 局域网面

9.1 SMB：托管系统共享

第一版不自研 SMB 协议栈（理由见 D-01）。做法是由网关托管 Windows 原生 SMB 共享：

  • 用 net share share /path=D:\share /grant:... 或 New-SmbShare 创建/更新共享，名称固定为 share
  • 只启用 SMB2/3：Set-SmbServerConfiguration -EnableSMB1Protocol $false
  • 匿名访问需要三项同时成立，缺一不可：
    • 服务端：EnableSMB2Protocol $true（默认）、Guest 账户启用、New-SmbShare -FullAccess Guest
    • 服务端策略：RestrictNullSessAccess 与 NullSessionShares 需把共享名加入
    • 客户端：Windows 10 1903+ 默认 AllowInsecureGuestAuth=0，必须改注册表才允许匿名 SMB2
  • 因此提供两种模式，配置项 smb.auth：
模式适用代价
guest安卓电视、小米电视原生播放器部分 Windows 与 iOS 客户端连不上，需客户端改注册表
accountiOS「文件」App、Windows 资源管理器建专用低权本地账户 fsgw，首次连接输一次口令
both默认推荐两条路并存，电视走匿名，手机走账户

账户模式的硬约束：Windows 默认策略禁止空密码账户远程登录（LimitBlankPasswordUse=1），所以口令不能为空，必须是真实密码。

9.2 写路径的能力边界

托管系统共享意味着网关不在写入路径上，这是 D-01 的直接代价。后果：

  • 无法在覆盖前硬链接旧内容，内容快照降级为 best-effort（见 02 第 6 节）
  • 写事件由 ReadDirectoryChangesW 事后送达，索引版本链不受影响（仍然准确），只有内容快照的承诺打折
  • 想恢复"写前捕获"，只有三条路：自研协议栈、写内核 minifilter、定时 VSS 快照，见 D-02

9.3 DLNA

  • 纯 Go DMS，指向 media=true 的白名单目录，只做发现与播放，不暴露文件管理
  • SSDP 多播用 239.255.255.250:1900，HTTP 服务用可配置高端口（默认 8200），避免与 SMB 抢权限
  • 媒体类型白名单：视频、音频、图片；不索引文档与压缩包
  • 小米电视自带播放器可零安装发现；同时保留 SMB 路径作为兼容退路（部分电视 DLNA 只认 MP4）

10. 外部只读面

10.1 WebDAV

  • 基于 golang.org/x/net/webdav，包装一层方法白名单 handler：只放行 GET、HEAD、PROPFIND、OPTIONS；其余（PUT/DELETE/MKCOL/MOVE/COPY/PROPPATCH/LOCK）返回 405 并记审计
  • PROPFIND 走 index 查库返回属性，不触碰磁盘
  • GET 先查库确认存在与大小，再回源读字节流；支持 Range，支持 ETag（用 content_hash，未算哈希时用 mtime-size 合成）
  • 路径映射：当前视图 /share/...，历史视图 /versions/...，两者都只读
  • 认证：HTTP Basic，口令 bcrypt 存配置；单口令全局生效，可选 per-share 口令
  • 默认绑定 127.0.0.1:8443，公网暴露靠反向代理或隧道（Cloudflare Tunnel / Tailscale / frp）。设计上不提供"直接监听 0.0.0.0:443"的一键选项

10.2 目录列举的性能账

ReadDir 直查 SQLite 不设内存缓存，这是讨论稿的明确选择。代价与缓解：

  • 单目录 1 万文件：SELECT ... WHERE parent_path=? ORDER BY name_key 走 (parent_path, name_key) 复合索引，配合覆盖索引可到毫秒级
  • 电视 SMB 客户端会频繁列举同一目录。缓解：协议层允许短暂的"同一路径 500ms 内重复列举"复用结果，但这是协议层的短生命周期快照，不是索引缓存，不引入失效问题

11. 控制台：前端 HTML，后端 Go

11.1 形态

控制台是网关的用户交互面，与三个协议面并列，但边界更严格：只在本机回环上运行，永不暴露给局域网或公网。

层选型约束
前端原生 HTML + CSS + 原生 JS，单页无 npm、无构建步骤、无 CDN 依赖（断网可用），embed.FS 打进二进制
通信fetch + EventSource（SSE）变更一律 POST + 自定义头，不用 GET 改状态
后端Go 标准库 net/http + Go 1.22 的 method-aware ServeMux零第三方框架
监听127.0.0.1:8444与 WebDAV 的 8443 用两套独立 mux 与中间件，不共用路由

不用 Electron / WebView2 的理由：它引入第二套运行时、升级链路和签名问题，而控制台需要的全部能力浏览器都有。代价是没有系统级文件选择框，靠 11.6 的目录浏览接口补上。

CLI 与 UI 共用同一个 HTTP API，不再单独实现命名管道：

浏览器 UI ─┐
           ├─▶ 127.0.0.1:8444 /api/*  ──▶ app 状态机 ──▶ 平台层
fsgw CLI  ─┘        （token 鉴权）

这样"开关"只有一条实现路径，验收也只需要验一处。

11.2 界面结构

单页五块，从上到下按"危险程度递增、使用频率递减"排列：

区块内容说明
总开关四态分段控件（OFF / LAN / WAN / ALL）+ 当前状态徽标 + 一键全关全关按钮独立配色，需二次确认
服务面SMB / DLNA / WebDAV 三张卡：监听地址、就绪状态、复制连接串（smb://192.168.x.x、https://…）连接串可直接发给手机
共享目录白名单列表、只读/媒体标记、增删入口增删走目录浏览接口选择
索引与快照文件数、待处理事件、写队列深度、最近重建；快照占用、版本数、配额条、清理按钮带 sparkline（手写 SVG，不引图表库）
诊断与审计匿名 SMB 客户端策略、445 占用、磁盘空间、防火墙规则状态；最近审计日志（可筛选"拒绝"）把 D-03 那类"连不上但不是 bug"的问题前置暴露

11.3 API 一览

所有接口前缀 /api，均需 token。变更类返回 202 + operation_id（开关是长任务，不能用一次请求的成败表示）。

方法路径用途备注
GET/api/status状态快照：四态、各面就绪、索引统计、快照占用前端首屏
GET/api/eventsSSE 推送：状态变化、队列深度、日志尾2s 心跳
POST/api/switch{state:"OFF|LAN|WAN|ALL"}二次确认字段 confirm
GET/api/operations/{id}长任务进度与失败阶段失败带 stage
GET/api/config脱敏配置（口令、hash 一律打码）

GET/POST/DELETE/api/shares白名单增删删除共享需 confirm

GET/api/fs/list列目录（仅子目录名 + 可写标记）见 11.6
POST/api/snapshot/gc立即清理
GET/api/audit审计分页查询since、limit、result
GET/api/diagnose一次性体检匿名策略、端口、磁盘、防火墙

11.4 本地网页的真实威胁：CSRF 与 DNS rebinding

控制台跑在 127.0.0.1，这不等于安全。用户浏览器里的任何网页都能向 http://127.0.0.1:8444 发起请求；DNS rebinding 还能让攻击者域名解析到回环地址，从而绕过同源限制读取响应。控制台一旦被第三方页面驱动去开 ALL，等于把共享直接推到公网。

四道防线，缺一不可：

  1. token：data/control.token，首次启动生成 32 字节随机值，写入时限定当前用户 ACL。前端从 URL fragment 取（不进 Referer、不进服务端日志），存 sessionStorage，之后每个请求带 X-FSGW-Token。服务端用 crypto/subtle.ConstantTimeCompare 比对
  2. Origin 校验：Origin 必须为空或等于 http://127.0.0.1:8444 / http://localhost:8444，否则 403
  3. Host 校验：Host 必须是 127.0.0.1:8444 或 localhost:8444。这是防 DNS rebinding 的关键一步——攻击者域名解析到回环后，Host 头仍是攻击者域名，直接被拒
  4. 不回 CORS 头，且变更接口要求自定义头。跨源带自定义头的请求会先发 preflight，我们不应答 Access-Control-Allow-*，请求根本到不了业务逻辑

补充：GET /api/fs/list 与 /api/audit 同样要鉴权，不要因为"看起来是只读"就放过——它们能泄漏本机目录结构。

11.5 长任务与状态推送

开关一次要动防火墙、起停监听、自检，不是一次请求能同步完成的：

  • POST /api/switch 立即返回 202 与 operation_id，实际执行在后台 goroutine
  • 进度与失败阶段通过 SSE 推给前端，同时 GET /api/operations/{id} 可主动查询
  • 失败时的 stage 直接对应 5.2 的五步，前端展示"卡在创建防火墙规则"，而不是笼统的"操作失败"

11.6 前端拿不到本地路径，所以需要目录浏览接口

浏览器出于安全不提供本地绝对路径，<input type="file" webkitdirectory> 只给相对路径。要"添加共享目录"就必须由后端列目录：

GET /api/fs/list?path=D:\
→ {"path":"D:\\","entries":[{"name":"share","is_dir":true},{"name":"backup","is_dir":true}]}

约束，全部在实现里硬编码，不做成配置：

  • 只返回子目录，不返回文件名、不返回大小、不返回内容
  • 只接受盘符根（D:\）或已配置共享根下的路径，拒绝 ..、拒绝 UNC（\\host\share）
  • 路径规范化复用 internal/vfs，与协议面同一套规则，不另写一份
  • 每次调用写审计（谁在什么时候浏览了哪个目录）

11.7 危险操作的产品层保护

技术防线之外，交互层也要拦一次：

  • 四态开关切换需二次确认（按钮变"确认开启 LAN？"），不只弹一个"确定/取消"
  • 从 WAN/ALL 回到 OFF 不需要确认，但从 OFF 到 WAN 必须显式说明后果（"外部可访问"）
  • 修改配置保存前展示 diff，只列出变更字段
  • 不在控制台提供"删除快照""清空索引"这类不可逆操作的一键入口，只提供带确认的单项操作

12. 版本与快照

语义定义与存储布局见 02-数据模型与事务.md。这里只固定三条对外承诺：

  1. 索引版本链（路径、大小、mtime、哈希、变更类型）对所有来源可信
  2. 内容快照对网关自身写路径（WebDAV 上传、内置页面）可承诺；对 SMB 来源为 best-effort，UI 上必须显示"该版本可能不完整"
  3. 移动与重命名永不产生版本。versions 表在移动事务中零写入，这是可被自动化验收的断言

13. 安全模型

三层，从外到内，任一层失效仍有兜底。

层手段失效后果
一层：开关即边界OFF 时零监听、零防火墙规则无
二层：协议最小化禁 SMBv1、WebDAV 方法白名单、445 只对 localsubnet、WAN 只绑回环攻击面扩大但需先过开关
三层：目录最小化共享根白名单、VFS 穿越防护、不共享系统盘单目录泄漏

额外措施：

  • 所有写操作记审计（时间、来源、路径、结果、客户端 IP），滚动文件，默认保留 30 天
  • WAN 面可选 IP 白名单与失败登录限速（同 IP 5 次失败锁 10 分钟）
  • 进程以 LocalSystem 运行时，防火墙规则命名为 FSGW- 前缀，便于人工核查与一键清理
  • 控制面单独成域：ctlapi 只绑回环、只接受带 token 的请求、校验 Origin 与 Host（防 DNS rebinding），与 WebDAV 用两套 mux 与中间件。控制面的威胁模型与协议面完全不同——它面对的不是"外部陌生人"而是"用户浏览器里的其它网页"，详见 11.4

14. 配置模型

config.yaml 放在 D:\fsgw\config.yaml（程序目录），与数据分离：

version: 1

dlna:

15. 可观测性

  • fsgw status：与 GET /api/status 同一份数据，CLI 只是做了格式化
  • GET /healthz（回环，免 token）：进程存活 + DB 可写。免 token 是为了让外部探针能打，因此只回 ok/degraded，不含任何细节
  • GET /metrics（回环，需 token，Prometheus 文本格式）：fsgw_events_total{op}、fsgw_write_queue_depth、fsgw_reconcile_duration_seconds、fsgw_snapshot_bytes
  • 控制台本身即主要观测面：状态、队列深度、审计尾都在 UI 上，不需要另开一套
  • 日志：结构化 JSON 行，滚动 20MiB × 5；审计独立文件，不复用调试日志

16. 包职责与依赖方向

依赖只能自上而下，platform 是最底层，不 import 任何业务包。

cmd/fsgw      → app
app           → config, index, vfs, smbhost, dlna, webdav, snapshot, audit, ctlapi, platform
ctlapi        → app(状态机), index(只读统计), config, audit, vfs(路径校验)
webui         → (纯静态资源，只被 ctlapi 通过 embed 引用，不 import 任何 Go 包)
vfs           → index, platform/fileid
webdav        → vfs, index, snapshot(只读)
dlna          → vfs, index
smbhost       → platform/firewall, config
snapshot      → index, platform/link
index         → (无业务依赖)
platform/*    → (仅 x/sys)

注意 webui 与 ctlapi 的边界：前端不知道任何业务规则，所有校验（可写性、路径合法性、状态机前置条件）都在 ctlapi 之后的 Go 侧完成。前端只负责展示与收集输入——这样即使前端被改坏，也不会绕过安全校验。

02 数据模型与事务

本文是编码时的逐条对照物。所有 DDL 可直接执行，所有断言都可被自动化验收。

1. 表结构与职责

shares ──┐
         ├─ share_dirs          白名单与可写性
         │
objects ─┴─ files              内容身份（file_id）与路径条目分离
            │
            ├─ versions        索引版本链（元数据版本，不产生于移动）
            ├─ snapshots       内容快照实体（可选，受影响于 D-02）
            └─ path_history    路径变更流水（移动只写这里）

pending_moves                  监听事件的配对中间态
suppress                       网关自身写入的事件抑制
reconcile_log                  范围重建记录
schema_meta                    迁移版本

核心建模决策：files 与 objects 分离。一个 object（内容身份）可以对应多个 files 行（硬链接、多共享），这样版本链挂在 object_id 上，天然符合"路径是属性、不是身份"。如果按讨论稿早期的"file_id 做主键"简化写法，硬链接场景会直接冲突。

2. 完整 DDL

PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
PRAGMA wal_autocheckpoint = 1000;

CREATE TABLE IF NOT EXISTS schema_meta (
  key    TEXT PRIMARY KEY,
  value  TEXT NOT NULL
);

-- 共享与白名单 ------------------------------------------------------------
CREATE TABLE IF NOT EXISTS shares (
  share_id      TEXT PRIMARY KEY,          -- 'main'
  root_path     TEXT NOT NULL,             -- D:\share（\?\ 前缀形式）
  root_key      TEXT NOT NULL,             -- 小写、正斜杠
  volume_serial INTEGER NOT NULL DEFAULT 0,
  writable      INTEGER NOT NULL DEFAULT 1,
  deny_delete   INTEGER NOT NULL DEFAULT 0,
  media         INTEGER NOT NULL DEFAULT 0,
  created_at    INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS share_dirs (
  id        INTEGER PRIMARY KEY AUTOINCREMENT,
  share_id  TEXT NOT NULL REFERENCES shares(share_id) ON DELETE CASCADE,
  rel_path  TEXT NOT NULL,                 -- '' 为根，'/private' 形式
  path_key  TEXT NOT NULL,
  writable  INTEGER NOT NULL DEFAULT 1,
  media     INTEGER NOT NULL DEFAULT 0,
  UNIQUE(share_id, path_key)
);

-- 内容身份 ----------------------------------------------------------------
CREATE TABLE IF NOT EXISTS objects (
  object_id      TEXT PRIMARY KEY,         -- UUIDv7，网关生成，跨卷移动时随迁移
  native_file_id TEXT,                     -- 'v2:<volser>:<hex32>' 或 'v1:<volser>:<hex16>'
  volume_serial  INTEGER,
  first_seen_at  INTEGER NOT NULL,
  last_seen_at   INTEGER NOT NULL,
  state          INTEGER NOT NULL DEFAULT 0  -- 0=live 1=gone 2=frozen
);
CREATE UNIQUE INDEX IF NOT EXISTS ux_objects_native
  ON objects(volume_serial, native_file_id);

-- 路径条目 ----------------------------------------------------------------
CREATE TABLE IF NOT EXISTS files (
  file_id     INTEGER PRIMARY KEY AUTOINCREMENT,
  share_id    TEXT NOT NULL REFERENCES shares(share_id) ON DELETE CASCADE,
  object_id   TEXT NOT NULL REFERENCES objects(object_id),
  parent_path TEXT NOT NULL,               -- '' 为根，'/' 分隔，小写
  name        TEXT NOT NULL,               -- 原始大小写
  name_key    TEXT NOT NULL,               -- 小写
  path        TEXT NOT NULL,               -- 完整相对路径（原始大小写）
  path_key    TEXT NOT NULL,               -- 完整相对路径（小写）
  kind        INTEGER NOT NULL,            -- 0=file 1=dir
  size        INTEGER NOT NULL DEFAULT 0,
  mtime_ns    INTEGER NOT NULL DEFAULT 0,
  content_hash TEXT,                       -- sha256 hex，延迟计算
  hash_state  INTEGER NOT NULL DEFAULT 0,  -- 0=none 1=queued 2=done 3=skipped 4=failed
  status      INTEGER NOT NULL DEFAULT 0,  -- 0=active 1=writing 2=stale 3=deleted
  last_source INTEGER NOT NULL DEFAULT 0,  -- 0=unknown 1=smb 2=gateway 3=local
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS ux_files_path     ON files(path_key);
CREATE UNIQUE INDEX IF NOT EXISTS ux_files_parent   ON files(parent_path, name_key);
CREATE INDEX IF NOT EXISTS        ix_files_object   ON files(object_id);
CREATE INDEX IF NOT EXISTS        ix_files_status   ON files(status) WHERE status <> 0;

-- 索引版本链 --------------------------------------------------------------
CREATE TABLE IF NOT EXISTS versions (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  object_id    TEXT NOT NULL REFERENCES objects(object_id),
  seq          INTEGER NOT NULL,           -- 从 1 递增，per object
  size         INTEGER NOT NULL,
  mtime_ns     INTEGER NOT NULL,
  content_hash TEXT,
  change       INTEGER NOT NULL,           -- 1=write 2=truncate 3=meta 4=appear
  source       INTEGER NOT NULL,
  snapshot_id  TEXT,                       -- 有内容快照时回填
  recorded_at  INTEGER NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS ux_versions_seq ON versions(object_id, seq);

-- 内容快照 ----------------------------------------------------------------
CREATE TABLE IF NOT EXISTS snapshots (
  snapshot_id  TEXT PRIMARY KEY,
  object_id    TEXT NOT NULL REFERENCES objects(object_id),
  version_id   INTEGER REFERENCES versions(id),
  content_hash TEXT,
  storage      TEXT NOT NULL,              -- 'link' | 'copy'
  rel_path     TEXT NOT NULL,              -- 相对 snapshot.dir
  size         INTEGER NOT NULL,
  integrity    INTEGER NOT NULL DEFAULT 0, -- 0=complete 1=partial（best-effort 结果）
  created_at   INTEGER NOT NULL,
  pinned       INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX IF NOT EXISTS ix_snapshots_object ON snapshots(object_id, created_at DESC);
CREATE INDEX IF NOT EXISTS ix_snapshots_created ON snapshots(created_at);

-- 路径历史 ----------------------------------------------------------------
CREATE TABLE IF NOT EXISTS path_history (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  object_id  TEXT NOT NULL REFERENCES objects(object_id),
  from_path  TEXT,
  to_path    TEXT,
  change     INTEGER NOT NULL,             -- 1=create 2=move 3=rename 4=delete 5=restore 6=unshare
  move_kind  INTEGER NOT NULL DEFAULT 0,   -- 0=n/a 1=single-volume 2=cross-volume-confirmed 3=unconfirmed
  moved_at   INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS ix_ph_object ON path_history(object_id, moved_at DESC);
CREATE INDEX IF NOT EXISTS ix_ph_from   ON path_history(from_path);

-- 事件配对 ----------------------------------------------------------------
CREATE TABLE IF NOT EXISTS pending_moves (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  cookie         TEXT NOT NULL,            -- Windows: '<seq>' 合成；Linux: inotify cookie
  change_type    INTEGER NOT NULL,         -- 1=from 2=to
  path           TEXT NOT NULL,
  path_key       TEXT NOT NULL,
  native_file_id TEXT,
  seen_at        INTEGER NOT NULL,
  state          INTEGER NOT NULL DEFAULT 0 -- 0=pending 1=paired 2=timeout
);
CREATE INDEX IF NOT EXISTS ix_pm_state ON pending_moves(state, seen_at);

-- 网关写入抑制 ------------------------------------------------------------
CREATE TABLE IF NOT EXISTS suppress (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  path_key        TEXT NOT NULL,
  expect_size     INTEGER,
  expect_mtime_ns INTEGER,
  expires_at      INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS ix_suppress ON suppress(path_key, expires_at);

-- 范围重建记录 ------------------------------------------------------------
CREATE TABLE IF NOT EXISTS reconcile_log (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  root_path   TEXT NOT NULL,
  reason      TEXT NOT NULL,               -- 'overflow' | 'timer' | 'manual'

ReadDir 的查询必须写成覆盖索引形式，避免回表：

SELECT name, kind, size, mtime_ns, status
  FROM files

注意：ix_files_parent 上带 path_key 而不是 parent_path 的等值，是为了让"路径解析"（按完整路径查）和"目录列举"共用同一索引。列举时 parent_path = ? 也走同一索引前缀。

4. 单写队列

SQLite 在 WAL 下多读单写。所有写操作经由一个 goroutine 串行化，避免 SQLITE_BUSY 抖动。

            ┌──────────────┐
事件/请求 ──▶│ structural   │cap 1024  ─┐
            └──────────────┘           ├─▶ writer goroutine ──▶ 事务 ──▶ DB
            ┌──────────────┐           │
事件/请求 ──▶│ content      │cap 8192  ─┘
            └──────────────┘

调度规则：

  1. 每次取任务时先非阻塞消费 structural，空才取 content。结构性变更延迟目标 ≤20ms，内容变更 ≤200ms
  2. 单事务最多 200 条写，超出拆批；拆分引入的是"多批次可见"而非"半提交可见"
  3. 写队列深度超 80% 时打 warn 日志并上报 metrics；超 100% 时丢弃内容类任务但保留结构性任务，被丢弃的内容变更由定期 reconcile 兜底
  4. 读连接池 8 条，全部 query_only=1，从结构上保证读路径不会误写

控制面（ctlapi）不特殊：/api/status、/api/audit 只走读连接池；/api/shares 写 shares/share_dirs 必须投递到同一个写队列，不允许开第二条写连接。控制台看起来"只是个界面"，但它对库的访问规则和 SMB 客户端完全一样。

5. 事务顺序

5.1 监听驱动的变更（SMB 与本机修改都走这条）

步骤动作可见性
1查 suppress，命中且 size/mtime 匹配则丢弃—
2分类事件（结构性 / 内容性）—
3取 FileID（删除事件除外，用路径匹配）—
4upsert objects（按 native_file_id 命中则复用，否则新建 UUIDv7）不可见
5结构性：写 files + path_history；内容性：写 files 元数据 + versions不可见
6COMMIT一次性可见
7异步入队：算哈希、抓快照、更新 snapshots.version_id事后

第 5 步与第 6 步之间不允许任何外部读取路径介入。ReadDir 只读已提交数据，天然满足。

5.2 网关驱动的变更（WebDAV 写、快照清理、reconcile 补录）

网关是写入方时，顺序不同：先登记 suppress，再动磁盘，再写库。

  1. 插入 suppress(path_key, expect_size, expect_mtime_ns, expires_at=now+30s)
  2. 执行磁盘操作
  3. 写库（同一事务内更新 files，追加 versions）
  4. suppress 记录保留到过期，期间到达的 watcher 事件被吞掉

若第 3 步失败但第 2 步成功，进入"库比盘旧"状态，由 reconcile 修正；同时把该条目 hash_state=failed 便于排查。不允许反过来"读到盘上有什么就改库"。

5.3 移动事务（重点）

一次移动 = 一个事务，versions 零写入。伪 SQL：

BEGIN IMMEDIATE;

-- 1. 找源条目
SELECT object_id FROM files WHERE path_key = :old LIMIT 1;

-- 2. 更新路径（object_id 不变，file_id 不变）
UPDATE files
   SET parent_path = :new_parent,
       name        = :new_name,
       name_key    = :new_name_key,
       path        = :new_path,
       path_key    = :new_path_key,
       updated_at  = :now
 WHERE path_key = :old;

-- 3. 追加路径历史
INSERT INTO path_history(object_id, from_path, to_path, change, move_kind, moved_at)
VALUES (:object_id, :old, :new, 2, :move_kind, :now);

-- 4. 目录移动时级联更新子项路径（同事务）
UPDATE files
   SET path = :new || substr(path, length(:old) + 1),
       path_key = :new_key || substr(path_key, length(:old_key) + 1)
 WHERE path_key LIKE :old_key || '/%';

COMMIT;

验收断言（可自动化）：

SELECT (SELECT COUNT(*) FROM versions WHERE object_id = :id AND recorded_at >= :t0) = 0
   AND (SELECT COUNT(*) FROM path_history WHERE object_id = :id AND moved_at >= :t0) = 1;

6. 内容快照：能力分级（重要）

这是全篇最需要如实说明的部分。D-01 把 SMB 改成托管系统共享之后，网关不在写入路径上，"写前捕获"失去了立足点。

6.1 为什么硬链接方案不成立

硬链接不复制内容，只增加目录项指向同一 inode。当文件被原地覆盖时，所有硬链接看到的是新内容。因此"写前硬链接"只有在写发生之前执行才有意义——而 SMB 客户端写入时，网关拿到的第一个事件已经是"写已经开始"。

唯一真正有效的写前捕获方式是：网关自己持有写句柄（自研协议栈），或内核 minifilter 拦截 create/write。两者都超出第一版范围。

6.2 分级承诺

级别内容来源承诺
L0 索引版本链路径、size、mtime、哈希、变更类型、时间全部来源可承诺。事后送达也足够，元数据不会丢
L1 网关写路径快照完整旧内容WebDAV 上传、内置上传页、reconcile 补录可承诺（写前登记 + 写前复制/链接）
L2 SMB 来源 best-effort首个 Write 事件时抓取当前字节SMB 客户端不承诺。大文件慢写通常能抓到较完整的前段；小文件覆盖基本抓不到
L3 粗粒度卷影整卷时点副本可选启用 VSS 定时任务时间粒度粗（默认 15 分钟），但完整、可靠、零协议改造成本

对外 UI 必须显示 integrity：L2 抓到的标记 partial，历史版本页显示"该版本可能不完整"。

6.3 存储布局

D:\fsgw\data\snapshots\
  ab\cd\abcdef...-1.bin        按 content_hash 前 4 位分两级目录
  ab\cd\abcdef...-1.json       伴生元数据（object_id, version, storage, size）

同卷优先 CreateHardLinkW（storage=link，零空间成本），跨卷退化为复制（storage=copy，异步限速，默认 20 MiB/s）。同一 content_hash 只存一份，snapshots 表通过多行引用同一 rel_path 实现去重。

6.4 清理器

独立 goroutine，每 10 分钟一轮，按顺序执行：

  1. 若可用空间 < min_free_gb：告警并按"最旧 + 最低价值"顺序清理，直到回升至阈值。绝不清理当前活动文件
  2. 应用保留策略：24h 内全留 / 7d 内每小时留一 / 30d 内每天留一 / 之后只留最新
  3. 应用每文件上限（默认 10 个内容快照）
  4. 应用总配额（默认 200 GiB）
  5. 清理 snapshots 行与磁盘文件保持同事务顺序：先删行（事务），再删文件（尽力，失败进回收队列重试）

7. 事件配对与超时定性

Windows 的 RENAMED_OLD_NAME / RENAMED_NEW_NAME 天然连续，但客户端崩溃、网络中断会导致只有一半。

状态流转：

收到 OLD_NAME → pending_moves(state=pending, change_type=from)
收到 NEW_NAME → 若存在同 cookie 的 from：
                  ├─ 取 NEW 的 FileID
                  ├─ 与 from 路径对应的 object 匹配（同卷 → FileID 相同）
                  └─ 执行移动事务（versions 零写入）
              → 若不存在 from：
                  └─ 视为外部移入：新建条目，path_history 记 create

超时扫描（每 2s，阈值 500ms）
  ├─ 孤立 from：源路径已不存在 → 判定为删除，path_history 记 delete
  ├─ 孤立 from：源路径仍存在 → 丢弃记录（假事件）
  └─ 孤立 NEW：按新建处理

跨卷移动：FileID 变化，走哈希 + 大小 + 时间窗口（±10s）匹配。匹配成功则迁移 object_id 归属，versions 不追加，path_history.move_kind=2；匹配失败则如实按"删除 + 新增"处理，move_kind=3 并打 move_unconfirmed 标记，不假装成功。

8. 一致性自愈

三类自愈任务，全部限定范围，禁止全盘扫描：

任务触发范围频率
子树重建watcher 溢出溢出事件给出的子树根事件驱动
存在性抽查定时最近 24h 变更过的 object6h
孤儿快照清理定时snapshots 中 object 已 gone 超过保留窗口24h

子树重建的分批策略：以子目录为单位提交，单批 ≤200 条。重建期间该子树在 files 上打 status=2(stale)，ReadDir 对 stale 条目仍返回旧值（可用性优先于瞬时准确性），最后一批提交时清除标记。这样避免"重建一半目录突然空了"的体验。

9. 迁移与版本

  • 迁移脚本以 internal/index/migrations/0001_init.sql 形式 embed 进二进制
  • schema_meta.schema_version 单调递增，启动时比对，只允许前滚
  • 迁移在单个事务内执行；失败则整体回滚并拒绝启动（不做部分迁移）
  • 破坏性变更（删列、改类型）必须新建表 + 复制 + 重命名，SQLite 的 ALTER TABLE 能力有限

10. 容量估算

以 20 万个文件、平均路径 60 字符估算：

  • files：约 60 MiB（含两个唯一索引）
  • versions：按每月 5 万次内容变更计，每年 60 万行，约 60 MiB
  • path_history：按每月 1 万次移动计，5 年约 60 万行，约 50 MiB

结论：单文件 SQLite 在五年量级内不需要分库。若超过 50 万文件，再考虑按共享分库或按年归档 versions。

D-01 SMB 实现路线：托管系统共享，还是自研协议栈

事实前提

纯 Go 生态里没有可用于生产环境的 SMB2/3 服务端实现。开源库绝大多数是客户端。服务端要正确处理 credit 授予、compound request、signing、encryption、lease/oplocks、durable handle、change notify、DFS 引用、IPC 命名管道等子协议，任何一项缺失都会让某类客户端连不上或行为异常。这是方案里唯一一个"看起来是技术选型、实际是可行性问题"的点。

备选

选项做法得到什么失去什么
A（推荐）托管 Windows 原生 SMB 共享，网关负责创建、配置、开关、索引电视与手机兼容性最好，零协议开发，稳定性等同系统网关不在写路径上，写前捕获做不了；匿名受系统策略约束
B自研 SMB2/3 服务端唯一能同时拿到写前捕获与精细 VFS 控制协议栈体量巨大，兼容性回归风险高，第一版几乎不可能稳定
C局域网写面改用 WebDAV实现成本最低，能与外部面复用代码破坏"零安装"，安卓电视与手机文件管理器体验极差
DA + VSS 卷影兜底保留 A 的兼容性，内容级历史由卷影提供时间粒度粗（分钟级），需要卷影权限与额外空间

推荐

第一版选 A，并把 smbhost 设计成可替换接口：

type Provider interface {
    EnsureShare(spec ShareSpec) error   // 幂等创建/更新
    RemoveShare(name string) error
    Status(name string) (ShareStatus, error)
}

两个实现：hosted（A，第一版）、native（B，v2 实验分支）。上层与协议无关，切换不动业务代码。

如果后续确认"必须写前捕获"，先评估 D，再评估 B。不要因为"方案里写了网关当 SMB 服务端"就硬上 B。

不决策的后果

M3 阶段会卡住，因为 smbhost 的接口形状取决于这个选择。

D-02 内容快照的承诺边界

事实前提

用户已确认"整个共享可读写"。但 SMB 走系统共享意味着删除与覆盖都由系统内核完成，网关拿不到任何前置钩子。硬链接保旧 inode 的技巧在就地覆盖场景完全失效（见 02 第 6.1 节）。

因此实际能承诺的只有：

  • 索引版本链（元数据）：全部来源，可信
  • 内容快照：网关自身写路径可信；SMB 来源只能 best-effort
  • 删除恢复：只有在快照存在时才能恢复，且 SMB 删除是不可拦截的真删

备选

选项承诺代价
A只做 L0 索引版本链 + L1 网关写路径快照，SMB 来源明确标注"无可靠历史"最诚实，但用户预期落差大
B（推荐）A + 可选启用 VSS 定时卷影（默认 15 分钟），对外把卷影时点作为"完整版本"呈现需要额外磁盘空间（增量，通常 5–15%），需要管理员权限，恢复粒度受间隔限制
C自研协议栈或 minifilter 实现真写前捕获见 D-01 B，第一版不可行

推荐

选 B，但把 VSS 做成"可选、默认关闭、显式开启时给出空间提示"。UI 三档标记必须清楚：

  • 完整：L1/L3 产出
  • 尽力：L2 产出，可能不完整
  • 仅元数据：只有 L0

不决策的后果

/versions 页面会出现"用户以为能下载三天前的文档，实际下到半个损坏文件"的情况。这比没有历史版本更糟。

D-03 匿名 SMB 在 Windows 上的真实可行性

事实前提

"局域网零安装"要求匿名访问。但 Windows 10 1903 之后，SMB2/3 的匿名（Guest）访问在客户端侧默认被拒绝，需要改注册表：

HKLM\SYSTEM\CurrentControlSet\Services\LanmanWorkstation\Parameters
  AllowInsecureGuestAuth = 1 (DWORD)

服务端侧还需要：Guest 账户启用、共享授权给 Guest、NullSessionShares 包含共享名、RestrictNullSessAccess 允许。

另外：

  • 安卓电视/小米电视原生播放器：通常支持匿名 SMB2，可用
  • iOS「文件」App：不支持匿名，必须账号密码
  • Windows 资源管理器：默认隐藏匿名共享，需启用"不安全的来宾登录"
  • Windows 默认禁止空密码账户远程登录（LimitBlankPasswordUse=1），所以账户模式的口令不能为空

推荐

配置 smb.auth: both：

  • 匿名路径服务电视
  • 专用低权本地账户 fsgw（随机口令，写在 config.yaml 与一页说明里）服务手机与 PC

首次连接时提示"iOS 需要账号密码"，不要承诺"所有设备都零配置"。

不决策的后果

验收时"手机连不上"会被当成 bug 排查很久，实际是客户端策略。

D-04 整个共享可读写的删除风险

事实前提

用户选择"整个共享可读写"。这意味着任何局域网设备可以删除 D:\share 下任何文件，网关无法拦截。

可选缓解（不影响已定策略）

  1. 默认开启 deny_delete=false，但提供 fsgw restore <path> [--at <time>] 从快照恢复
  2. 可选 deny_delete=true：通过共享 ACL 实现只读删除（Change 权限去掉 DELETE），代价是客户端删除操作报错而非静默
  3. 每日一次 snapshots.pinned 快照（不受配额清理），成本可控

推荐

保留用户选择（可读写可删除），但默认启用 1 + 3，把"误删恢复"做成可用功能而不是事后解释。

D-05 跨卷移动的定性

同卷移动有硬保证（FileID 不变）。跨卷移动只能哈希 + 大小 + 时间窗口匹配，属于尽力而为。

推荐

如实按 02 第 7 节处理，匹配不上就记"删除 + 新增"并打 move_unconfirmed。不要为了让路径历史看起来漂亮而强行合并——错并会把两个不相干文件的版本链混在一起，比丢失更危险。

第一版共享根只有 D:\share 一个卷，跨卷场景实际不会触发。但要保留代码路径，因为将来加第二个共享根（比如移动硬盘）就会遇到。

D-07 "无缓存层"的性能风险

讨论稿明确选择"目录列举直查 SQLite，不设内存缓存"。这在 Windows 上有一个具体风险：电视 SMB 客户端列举大目录（数千文件）时会高频重复请求。

缓解

  • 覆盖索引 + ORDER BY 走索引，实测目标为 1 万条目 <50ms
  • 协议层允许 500ms 内的同路径重复列举复用结果（短生命周期、无失效问题）
  • 若实测不达标，退路是加"目录条目计数 + 版本号"的极简缓存：目录内容变更时版本号 +1，缓存键含版本号，天然无失效问题

定性

这是性能风险，不是正确性风险。正确性上无缓存的设计明显更优（移动语义精确、无失效 bug）。先按无缓存实现，实测不达标再上版本号缓存，不要提前优化。

D-08 DLNA 库选型

需要在 T-31 阶段评估。约束：

  • 必须支持 Windows 下的 SSDP 多播（多网卡时需指定接口，否则可能只在一个网卡上广播）
  • 必须支持自定义 ContentDirectory 后端（从我们自己的索引取数据，而不是扫目录）
  • 必须允许只暴露媒体类型

候选方向：anacrolix/dms 的分层结构可参考，但其内置文件系统后端需要替换成索引后端。若改造量超过自研 SSDP + SOAP 最小集（只需 Browse + 媒体 URL），则自研更可控。

定性：中等风险，可延后到 M4。

D-09 权限模型：服务以 LocalSystem 运行

网关需要三样提权能力：增删防火墙规则、创建 SMB 共享（net share / New-SmbShare）、读卷序列号。

以 LocalSystem 跑服务是最省事的路径，但意味着网关进程被攻破即等价于系统管理员。考虑到网关的对外面是只读 WebDAV 与匿名 SMB，这个风险不能忽略。

缓解

  1. WebDAV 处理器严格白名单，路径校验在 VFS 单点完成，不允许任何字符串拼接后直接 os.Open
  2. SMB 面不经过网关进程（系统提供），网关进程不解析任何来自 SMB 客户端的字节
  3. 只读面与提权能力分离：v2 可考虑拆成两个进程（fsgw-core 无提权 + fsgw-priv 有提权，通过命名管道通信，接口只暴露"加规则/删规则/建共享/删共享"四个动作）

推荐

第一版单进程 LocalSystem，但把提权操作收敛到 internal/platform 的四个函数，为 v2 拆进程留出切面。
